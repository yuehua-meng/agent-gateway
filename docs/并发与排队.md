# 并发与排队

为了让内部项目直接共享容量 → 使用单进程 asyncio 入场控制和图片 FIFO 队列 → 平时有空位立即执行，异常拥堵时有明确上限。无需新增中间服务或业务埋点。

## 配置

下面是合并进网关根目录 `config.json` 的顶层字段，不是完整配置文件：

```json
{
  "text_concurrency": 200,
  "image_concurrency": 10,
  "image_queue_limit": 6,
  "image_queue_timeout": 60
}
```

| 字段 | 默认值 | 校验范围 | 含义 |
|---|---:|---|---|
| `text_concurrency` | 200 | 整数 1–1000 | 文本全局执行名额，满了不排队 |
| `image_concurrency` | 10 | 整数 1–100 | 图片全局执行名额 |
| `image_queue_limit` | 6 | 整数 0–100 | 额外图片等待数；0 表示不排队 |
| `image_queue_timeout` | 60 | 大于 0、最多 480 秒 | 图片最长等待时间 |

修改后需重启。旧配置字段 `text_queue_timeout` 仍可读取，但不再生效。没有每项目并发或排队上限，项目日次数和模型授权仍然生效。

## 请求行为

- 单项目来 20 个文本请求，空闲时可以全部执行；200 个文本执行名额都已占用时，新文本返回 `429 / GATEWAY_BUSY`。
- 图片最多 10 个执行、6 个等待，第 17 个新图片请求返回繁忙。图片等待不占文本名额。
- 图片按等待顺序获取空位。等待时间计入总时限：总时限 260 秒、已等 60 秒时，后续执行最多剩约 200 秒；不是排队后重新计时。
- 重试、切换和退避属于同一次操作，继续占同一个执行名额；每次实际上游尝试仍计入项目日次数。
- 任务完成、失败或取消会归还名额。客户端断开不主动取消已受理工作，后台操作仍受总时限约束。

这是共享容量保护，不保证项目公平，也不是持久化任务队列。200/10 是配置上限，模拟并发测试验证了调度正确性，不代表真实厂商配额或生产性能。

## 繁忙后如何重试

| 情况 | 是否请求上游 | 同一幂等键再次提交 |
|---|---|---|
| 入场时执行/等待名额已满 | 否，不创建新操作 | 相同内容可稍后重试 |
| 图片排队超时 | 否，记录无尝试的失败操作 | 相同内容可重新入场，保留操作 ID |
| 相同操作仍执行或排队中 | 不重复请求 | 返回 202 和操作查询地址 |
| 相同操作已成功 | 不重复请求 | 返回缓存结果；缓存过期返回过期错误 |
| 图片上游超时、结果未知 | 可能已受理 | 不自动重发，先到供应商核对 |

`GATEWAY_BUSY` 的 `retryable=true` 仅表示可以稍后再试；客户端应有限次数、带间隔重试，避免立即无限循环。更改内容后不能复用同一幂等键。

## 代码与验证

- [admission.py](../gateway/admission.py)：`reserve` 占位，`release` 归还和唤醒，`snapshot` 提供容量。
- [main.py](../gateway/main.py)：`submit` 先处理幂等命中；建操作与占位之间没有异步让出。
- [storage.py](../gateway/storage.py)：`claim` 允许没有上游尝试的繁忙操作重新提交。
- [engine.py](../gateway/engine.py)：`execute` 控制等待和总时限；`launch` 处理尚未开始执行就被取消的名额释放。
- [config.py](../gateway/config.py)、[run.py](../run.py)：配置校验、连接池与 HTTP 入口保护。默认入站保护为 280，给业务连接和管理请求留出余量；连接数不等于模型并发数。
- [test_admission.py](../tests/test_admission.py)：200 文本 + 10 图片 + 6 等待、超载、幂等、数据库异常、取消及截止时间测试。
